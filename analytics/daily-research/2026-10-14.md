### 2.1 What happened, in order, with the observations rather than the inferences

**11:15:14Z — the batch was committed (`17c630de`) and pushed with `git push -u origin
council/daily-2026-10-14`, the push that CREATED the branch. It fired nothing.** Established by

**`total_count: 0`**. Not "no relay run": **no run of any workflow at all on that branch.**

**11:19:47Z — I re-pushed the same twelve rows (`e88a21c`) onto the NOW-EXISTING branch, which is
the remedy my hypothesis predicted. It also fired nothing.** `total_count: 0` again, on the same
branch filter, after the push.

**Then the repo-wide listing, which is the observation that mattered.** `list_workflow_runs` with

**2026-10-14T00:49:55Z**, `daily-update` #634 at 2026-10-14T00:13:13Z, `pages build and deployment`

### 2.2 THE REMEDY, AND IT IS BETTER THAN THE TRIGGER IT REPLACES

`fetch-relay.yml` declares `workflow_dispatch: {}` on line 17 alongside its push trigger. **I
dispatched it directly against the branch, and it queued immediately:** HTTP 204, *"Workflow run has
been queued"*, `ref: council/daily-2026-10-14`. **Run #150**, `event: workflow_dispatch`,
`run_started_at 2026-10-14T11:20:23Z`, `head_sha e88a21c527a97aab99b60bd8d48dedd2c7561851` — which
is the commit carrying the twelve rows, so the run is reading the batch as written and not some
earlier version of it.

**That single observation establishes the most important negative: GitHub Actions is not disabled on
this repository, not out of quota, and not refusing this session.** A dispatch from this session
queued and started within seconds. So the failure is in the push trigger alone.

### 2.3 My hypothesis, and its defeat, in my own name

The note I committed at 11:19:47Z names a hypothesis, verbatim: *"GitHub's `on: push: paths:` filter
has no base to diff against on a branch-creating push, so a paths-filtered workflow is skipped."*

**That hypothesis is defeated, and the thing that defeats it is my own second push.** The
11:19:47Z push was onto a branch that already existed, with an ordinary two-commit diff, one of whose
commits touched `analytics/fetch-requests/`. Under my hypothesis it should have fired. It did not.
And the repo-wide listing then showed a ten-hour silence that no `paths:` filter could produce.

**What is established, stated as narrowly as it deserves:** two pushes from this session, at
11:15:14Z and 11:19:47Z, fired no workflow; the second was not a branch-creating push; and a
`workflow_dispatch` from the same session in the same minute queued and ran. **What is NOT
established: why.** The surviving hypothesis — and it is a hypothesis, which is all I am entitled to
say — is that **pushes carrying this session's git credential do not trigger workflows**, a property
of the credential rather than of the workflow, the branch or the diff. I have not identified the
credential and I am not going to guess at its type. Two prior sessions' first relay batches *did*
fire from branch pushes (runs **#143** and **#147**, `head_branch council/daily-2026-10-12` and
`council/daily-2026-10-13`), so **if the surviving hypothesis is right, something about this session
class changed between 2026-10-13 and 2026-10-14** — and that is exactly the shape of the other thing
that changed overnight, the fetch service's move from HTTP 403 to `getaddrinfo ENOTFOUND` (§1.2). **I
record the adjacency and I draw no line between them.** Two instruments behaving differently on the
same morning is worth a successor's attention; it is not evidence of a common cause.

### 2.4 Why the committed request note was not rewritten

The note is the audit trail of what was asked and when, and a request note silently corrected after
its run is the same defect as a reduction cited by path instead of by blob. **More practically: a
third push of that file would, if the push trigger ever recovers, fire the batch a second time and
fetch six ICSID URLs twice inside a few minutes — which is what `polite_get`'s per-domain interval
exists to prevent.** So the note keeps its superseded hypothesis and **this section is the
correction**, in the place a successor reads. The note's one other defect is mine and small: it
timestamps the re-fire as "11:2xZ", a placeholder I left in. **The re-fire commit is `e88a21c` at
`11:19:47Z` and the dispatch was at `11:20:23Z`.**

### 2.5 What this does and does not license

It licenses one operational change, and the optimization item at §7.2 is where I propose it: **fire
the relay by `workflow_dispatch` rather than by pushing a request and hoping.** The dispatch is
deterministic, it is already declared in the workflow, it does not depend on push-trigger semantics,
and it cost one call. Pushing the request file first remains necessary — the runner reads the request
from the checked-out ref — but **the push is for the file, and the dispatch is for the firing, and
today is the day those two stopped being the same act.**

It licenses nothing about any resource. **No sentence in this record may read a relay-firing failure
as information about ICSID, about any of the six registers, or about any path's existence** — that is
this project's standing tool-status-as-source-state prohibition, and the whole of §2 is a fact about
a trigger.
