### §4 — Group C: the pre-flight worked, and it found a compliance defect

Row 5 returned `ok`/200, `content_type: "text/plain"`, `bytes: 150`, `find_matched: true`, and this excerpt in full:

> `User-agent: * Crawl-Delay: 5 Disallow: /rss Disallow: /search Disallow /record/*/export/*$ Sitemap: https://digitallibrary.un.org/sitemap_index.xml.gz`

**(a) Yesterday's caveat is discharged empirically for this file, and only for this file.** The caveat was that the 400-character excerpt *"establishes REACHABILITY and the HEAD OF THE FILE, never the full policy."* Here `len(excerpt) == 150 == bytes`, and 150 is well under `EXCERPT_CHARS = 400`, so no truncation occurred and the whitespace-normalised excerpt exhausts the file's textual content. **(b) The origin's own policy corroborates 0808-C4, at one day's remove.** I parsed the reconstructed file with `urllib.robotparser` — the same parser `src/sources/base.py:159-160` uses — under the project's own User-Agent. `can_fetch` returns **False** for `/search` and `/rss`, **True** for `/record/<id>`, `/record/<id>/export/…`, `/robots.txt` and `/`. The bound: this is the file served at 2026-08-09T11:16:36Z, and the 08-08 outcome was produced by whatever file was served at 11:17:09Z on 08-08, which we never retrieved. Corroboration is contingent on stability across one day, and I state it that way rather than as identity.

**(c) The colon-less line, which is the reason the full file mattered.** `Disallow /record/*/export/*$` has no colon where the two lines above it do. Python's `RobotFileParser.parse` splits each line on `:` and processes only lines that split into two parts, so a colon-less line is **skipped entirely**; my parse confirms it, returning `True` for the export path the line was evidently meant to forbid. RFC 9309's grammar likewise requires the colon and directs conformant parsers to ignore lines that do not match the grammar. **Our parser and a standards-conformant one read that line the same way: as absent.** So the admissibility map is: on `digitallibrary.un.org`, the only paths closed to this client are `/rss` and `/search`. **The record route is admissible to our own client** — which converts the blocker on that route from "unknown admissibility" to "we hold no record id", and an id cannot come from the relay, because obtaining one is discovery. The route is still **untested and not recorded as tried**; what changed is that the reason it is untested is now a single, nameable, operator-shaped gap.

**(d) `Crawl-Delay: 5` is silently ignored, and this is a live defect.** `src/sources/base.py:28` sets `MIN_INTERVAL_SECONDS = 3.0`, and `_respect_rate_limit` (`:186-200`) is the only interval enforcement in the client. `grep -rn "crawl_delay\|Crawl-Delay\|crawl-delay" --include=*.py .` returns **nothing**: the parser exposes the value — my parse returns `crawl_delay(UA) == 5` from this very file — and no code path ever reads it. The host asks for five seconds; the client would give three. Two honest bounds: `Crawl-Delay` is a non-standard extension absent from RFC 9309, so this is a gap against the host's expressed preference rather than against the exclusion standard; and it has not yet bitten, because every request this project has ever made to that host was either refused by our own robots layer or was a single row.

**(e) The defect I did not expect to find, and it is the sharper one.** `robots_allowed` fetches robots.txt with `requests.get` **directly** (`base.py:157`), outside `_respect_rate_limit`, and `polite_get` calls it *before* `_respect_rate_limit(domain)` (`:249` then `:255`). On the first fetch to any domain in a process, `_last_request_at` has no entry, so `wait` is 0 and the page request goes out immediately after the robots request. **Two requests to the same host, back to back, with no enforced interval — on every domain, every run.** Today's batch did this three times.
