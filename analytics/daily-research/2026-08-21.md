## Part II(b) — Escalation `N1` is RESOLVED as to mechanism, yesterday's diagnosis of it was wrong, and the fix is a discipline this chairman can execute today without touching a single workflow file

Yesterday's close-out opened on `N1` and called it the most consequential thing in the record: the operator
was emailed the 2026-08-20 record at **11:38:39 UTC**, when it held three Parts and none of the vetting
round, and thirteen binding objections were sustained after that email went out. The diagnosis was
*"the emailer's schedule is not coupled to whether the council has finished"*, and the proposed fixes were
all operator-side workflow edits.

**The diagnosis is wrong, and I can show it rather than argue it.**

### What the workflow actually does

`.github/workflows/daily-update.yml` fires on three things: a push touching
`analytics/daily-research/**`, crons at **12:00, 15:00 and 18:00 UTC**, and a 21:00 escalation cron. Its
own header comment says the routine's `[skip ci]` commits will *not* fire the push trigger and that "the
real delivery path is the recurring cron". A send writes a marker at
`analytics/daily-research/.sent/<DATE>` which de-duplicates every later run that day.

**11:38:39 is not 12:00, 15:00, 18:00 or 21:00.** So a cron did not send yesterday's draft, and the
workflow's own stated design did not fail. Something fired the push trigger.

### What fired it

Every one of yesterday's fourteen `analytics/daily-research/` commits carries `[skip ci]` — I checked all
fourteen, and none is the culprit. The GitHub Actions run list for `daily-update.yml` gives the answer
outright. **Run 277, id `32364771424`, `2026-08-20T11:38:14Z`:**

- `event: push`
- `head_branch: council/2026-08-20` — **a branch, not `main`**
- head commit: **`council: daily meeting 2026-08-20 (part 4) — second pre-registered relay batch, 7 rows`**

That head commit is the **relay request** for yesterday's second batch. It carries no `[skip ci]` —
**and it must not**, because `analytics/fetch-requests/README.md` states in terms: *"Do not put `[skip ci]`
in the request commit message — it suppresses the run."* Suppressing it would kill the relay, which is
this council's only retrieval channel.

So the mechanism is a **collision between two workflows that are each individually correct**:

- `fetch-relay.yml` requires the request commit to be **un-skipped**, or no retrieval happens.
- `daily-update.yml` fires on **any branch** and evaluates `[skip ci]` on the **head commit of the push**.
- Yesterday's session pushed the record commits and the relay-request commit **in one push**, with the
  un-skippable relay request as the head. GitHub therefore did not skip the push; `daily-update`'s path
  filter matched the record file that was also in it; and the mid-session draft was emailed from a
  feature branch.

Two corollaries follow, and the second is worse than yesterday's version of `N1`.

**First, the corrected record was never sent.** Run 279 at `12:13:47Z` is the push of the PR #93 merge to
`main` — the complete, thirteen-objections-applied record. It fired `daily-update` and succeeded. But the
`.sent/2026-08-20` marker had been written at 11:38:39, so the de-duplication did its job and **suppressed
the good version.** The marker cannot distinguish "already sent" from "already sent the wrong thing". The
operator received exactly one email yesterday and it was the draft.

**Second, this is not about scheduling at all**, so none of yesterday's three proposed fixes — gate on a
completion marker, move the cron later, require a `Record closed` line — would have prevented it. All three
address the cron path. The send came through the push path, from a branch, and would still come through it.

### The fix, which needs no code and is available to every future chairman

**Never put a relay-request commit and an `analytics/daily-research/**` commit in the same push.** Push the
relay request **alone**, before the record file exists or in its own isolated push; carry `[skip ci]` on
every record commit; and let the record reach the operator from `main`, after the merge, via the push the
merge itself makes or the next cron. Both workflows then behave exactly as documented.

**I did this today — and I have to record that I did it for the wrong reason.** Today's relay request was
pushed at the top of the session, alone, because firing early buys runner time and proves pre-registration
by commit order. That it also isolated the un-skippable commit from the record was **a side effect I had
