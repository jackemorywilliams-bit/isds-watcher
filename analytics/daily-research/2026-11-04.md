watchdog has never been capable of paging anyone, and I can show it rather than argue it.**

`.github/workflows/heartbeat.yml` runs daily and is documented in `HANDOFF.md` as *"a
dead-man's switch for the daily meeting. If the newest `analytics/daily-research/*.md` is
older than ~36h, or none exists, it emails an ALERT."* Its freshness test is
`os.path.getmtime(newest)` compared against `time.time()`, with `STALE_HOURS: "36"`.

**The defect is that it measures the wrong clock.** The job begins with
`actions/checkout@v4`, and git does not preserve modification times — a checkout writes
every file fresh, so each file's mtime is the moment the runner wrote it, a second or two
before the test runs. **`age_h` is therefore always approximately zero, whatever the record's
real age, and the stale branch is unreachable.** The only condition that can still fire is
the `no paths at all` branch, which would require the directory to be empty.

**Measured, from the run that matters.** Heartbeat run **128** (`41756935101`) executed at
**2026-11-04T01:52:05Z** against `main` at `b4a492c6`, where the newest daily record was
`2026-11-02.md`, last committed at **2026-11-02T12:15:01Z** — a true age of **37.6 hours**,
which **exceeds the 36-hour threshold**. Its log reads, verbatim:

> `newest record: 2026-11-02.md (~0.0h old)`
> `heartbeat OK — daily meeting is fresh.`

**So this is not a near miss on a threshold. The record was stale by the watchdog's own
standard, by more than an hour and a half of margin, and the watchdog reported it fresh with
an age wrong by 37.6 hours.** Had the clock been right, the operator would have been paged
about the missing 2026-11-03 sitting roughly nine hours before this session opened, and I
would have been told rather than having to find it.

**Two further gaps I name without proposing code**, since the one optimization item is
§5.5's and I am barred from building anything today.

1. **Even a corrected clock would not watch the right thing.** Every guard this project has
   reads `main`. The failure mode that actually occurred — a complete record sitting on an
   unmerged branch — is invisible to all of them, because from `main`'s point of view a
   stranded sitting and a sitting that never ran are the same event. Nothing enumerates
   `council/*` branches for unmerged records.
2. **The 36-hour threshold is deliberately slack** — the workflow's own comment says *"a
   single missed day does not page; two missed days does."* That is a defensible design for a
   watchdog, but combined with a self-merge model in which each sitting is solely responsible
   for landing its own output, it means one lost sitting is invisible by design and the loss
   is only detectable once a second one follows.

**The honest caveat the workflow states about itself remains true and is untouched by this**:
its alert travels over the same SMTP path as the thing it watches, so a dead SMTP path loses
the alert with it. **That caveat is a real limitation the author documented. The mtime bug is
not documented anywhere, and it defeats the check completely rather than partially.**

**I have changed nothing.** `.github/` is outside this session's merge scope and every
build-type item on this council's docket stands pending the operator's approval, not granted.
This is a measurement and an escalation, not a patch — see §5.5 and escalation **N17** at
§5.11.

### 2.7 The recovered sitting fired today's search a day early — and the duplicate produced the one thing neither sitting could produce alone

**I authorised one search call today as an unfired item. The 2026-11-03 analyst had already
fired it.** Its ten links are enumerated in that record at its §2.1. That is the duplicate
spend §1.4 counts as a cost of the stranding, and I do not take it back. **But comparing the
two is the most informative thing available today, and it is available only because the
record was recovered.**

**The measurement.** Same query string, verified character-identical. Same filter,
`allowed_domains: ["icsidfiles.worldbank.org"]`. Fired one day apart, by two different
research-analyst instances in two different containers. Compared on a scheme-and-case-
normalised URL match:

- **Membership: identical. 10 of 10 overlap, in both directions. Zero links in one set and
  not the other.**
- **Order: all but one position identical.** Positions 8 and 9 are transposed
  (`C2000/DC4466_En.pdf` and `C5946/DC10956_en.pdf` swap); positions 1–7 and 10 match
  exactly.
- Both calls: 10 of 10 links on `icsidfiles.worldbank.org`, 10 of 10 `.pdf`, zero
  out-of-set, zero prohibited-host. **No leak on a host-exact single-entry allow list, on
  either firing.**

**Why that is worth recording, and why it is not the cheerful finding it looks like.** Both
sittings declared, in advance, a staleness confound: engine result sets are not stable over
time, so a one-call observation against a nine-day-old comparator is not a controlled
experiment. **On this pair that confound did not materialise at all.** But the corpus holds
a directly contrary observation that I screened before writing this, and it is stronger than
today's: `analytics/insights.jsonl:233` (2026-10-04) records a **byte-identical** query
re-fired **minutes apart in one session** whose firings shared **zero** URLs — pairwise URL
Jaccard `0.000` on one pair, 19 distinct URLs across three firings of one string — and
concluded that *"sensitivity is a per-call stochastic property, not a standing one."*

**So the council now holds one Jaccard-0.000 pair minutes apart and one Jaccard-1.000 pair a
day apart, and I will not pretend to reconcile them.** The two observations differ in **both**
the query string **and** the filter, so neither variable is isolated and this is not a
controlled comparison. I record the contrast and name the live hypotheses without choosing:
either stability is a property of a host-exact single-host restriction, or it is a property
of these particular strings, or the engine's determinism varies per call in a way neither
observation samples. **A saturation reading — that one host simply holds ten responsive
documents and the call exhausts them — is available but is not supported by the corpus: the
committed search corpus holds 22 distinct `icsidfiles.worldbank.org` URLs, so the host
demonstrably serves more than ten, and the same string under `blocked_domains` on 2026-10-26
returned only three of them.** What reproduced is a *ranking*, not an exhausted population.

**A second stranding cost, concrete and still live.** The 11-03 analyst's search was never
committed as an artefact. That branch touched exactly three paths, and
`analytics/search-results/2026-11-03.json` is not among them — **the 11-03 call exists only
as prose inside a daily record.** Every novelty screen this council runs reads
`analytics/search-results/*.json`, so **that call is invisible to every future screen.** The
effect is already measurable: against the committed search corpus, nine of today's ten links
score as never-before-seen, when in fact all ten were returned yesterday. **A seat screening
tomorrow would call this arm novel again.** I am not writing a 2026-11-03 search artefact —
fabricating a machine-readable record of a call I did not make, in a seat's name, is exactly
what the real-agents rule forbids — so the gap stands and is escalated at §5.11 as **N18**.
