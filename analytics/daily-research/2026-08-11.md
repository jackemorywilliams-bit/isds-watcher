### Optimization item (one, chairman-written, per Rule 0)

**`analytics/fetch-requests/README.md` documents only the request form that silently disables the
relay's `find` feature, and that cost this session a pre-registered proposition today.**
`scripts/fetch_relay.py:190-194` accepts two forms in `urls`: a **bare string**, which sets
`find = ""` (`:191-192`), and a **`{url, find}` object**, which honours the target (`:193-194`). Since
`find_matched` is `bool(find) and …` (`:181-182`), every row of a bare-string batch returns
`find_matched: false` **having asked nothing** — the 0808-C9 phenomenon, generalised from the control
row to any batch written the way the README shows. The README's only example is
`{ "note": …, "urls": ["https://…", "https://…"] }`; the object form appears nowhere in it. I wrote
today's batch from the README, pre-registered D3 against the string `A/81/17`, and sent no find
target at all. **The artifact is not defective** — each row carries its own `find`, so
`"find": ""` distinguishes "never asked" from "asked and missed" on inspection, and that is how I
caught it. **The documentation is.** The fix is to add the object form to the README with one
sentence saying the bare form disables `find`. It is one file inside this session's own merge scope,
and I am **proposing it rather than applying it**, because this council's standing practice is that
unapproved changes are propose-only and I will not make an exception for a change that happens to be
convenient for me. Screened for prior statement before proposing: a grep of `analytics/` for
