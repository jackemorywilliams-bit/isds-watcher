### 4. One proposal

**Component:** `scripts/source_analytics.py` (report generator) reading `state/source_health.json` + `meta.json["source_health"]`, which `src/source_health.py` already computes.

**Change:** add a `Health` column to `analytics/source-receptivity.md` carrying each source's latest status and consecutive-zero streak, labelled "as of <latest run date>".

**Why this is not covered elsewhere.** The instrument already computes exactly the distinction the analytics officer said it could not make. `src/source_health.py` persists per-source zero streaks, escalates to `DEGRADED (n zero runs)` at three, and raises a `COLLECTION ANOMALY` warning — all tested in `tests/test_source_health.py`. But the receptivity ledger, which is the artifact the council reads to decide which sources earn their place, never sees any of it. So the officer hand-reconstructed it: Part 4 §1 and the whole of §4 ("longitudinal zero-streaks for the chairman's and the operator's attention") are a manual transcription of data the pipeline already generates, repeated every session, against a seat rule that exists *because* hand-copying is error-prone. Its §4 item 2 — "`gmail_scholar` — whether genuinely quiet or silently broken cannot be distinguished from the metadata" — is answerable today; the answer is just in a file the report does not open.

**Source:** dbt's source-freshness model — [Add sources to your DAG, docs.getdbt.com](https://docs.getdbt.com/docs/build/sources) (verified by fetch this session): a source declares `freshness: {warn_after, error_after}` against a `loaded_at_field`, and `dbt source freshness` emits a per-source pass/warning/error status into a machine-readable `sources.json` artifact. The transferable point is the separation the project currently lacks: source health is a first-class, generated, per-source status published *alongside* the source's output, not something a human re-derives from raw run logs.

**Effect:** the analytics seat stops re-deriving source health by hand each session; a source's zero row becomes self-explaining ("0 surfaced, RETURNED, 4-run zero streak" versus "0 surfaced, DEGRADED"); and the officer's §4 list becomes a generated column rather than a manual finding.

**Effort:** low. **Risk/tradeoff — and this is the guardrail, not a footnote:** the report is longitudinal (all runs) and health is point-in-time (latest run). Publishing them in one table without an explicit "as of <date>" label would reintroduce precisely the window-mixing failure this session just fixed, one column over. The label is a condition of adoption, not a nicety.

**Sequencing:** propose landing this *after* the same-window fix, as a separate change. Bundling an enhancement into a defect repair is how a clean fix becomes hard to review or revert.

**Dedup:** checked against all 22 log entries. Every existing entry targets research method, monitoring cadence, treaty-text retrieval, the fingerprint, or the multi-agent roadmap; none touches the analytics report, source health, or instrument observability. Genuinely new.
