### 1.4 The fetch relay is committed and working, so no fetch-dependent item is stranded

`scripts/fetch_relay.py` and `.github/workflows/fetch-relay.yml` are committed. The mechanism:
the session commits a request file, the push fires the workflow on a GitHub Actions runner that
*does* have egress, and the runner commits back a **reduction** — url, final url, status,
content-type, byte length, sha256, timestamp, user-agent, and one excerpt capped at 400
characters. The third-party document itself never lands in any file, branch, artifact or log;
the repository is public and a commit is publication. Compliance is inherited rather than
re-implemented: every request goes through `src.sources.base.polite_get` unchanged, so the same
identifying User-Agent, the same `robots.txt` evaluation and the same per-domain interval apply.

It last ran yesterday and it worked: `analytics/fetch-requests/` holds **76** requests,
`analytics/fetch-results/` holds **75** paired results, newest `2026-10-09-daily.json`, whose
six rows all returned `outcome: ok` at HTTP 200 with `control_ok: true`. **So "fetch is dead"
does not make a fetch item stranded in this session class, and I have not described any item
that way.** What the relay cannot do is discover: it tests substring presence in visible prose
for literals a seat already knows, on a 19-entry host allowlist. It can refute "is this party on
this page" and it can never establish a subject-matter absence.
