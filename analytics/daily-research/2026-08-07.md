### Verify / be skeptical

- **`status: "500"` is an origin answer, not a relay fault — and it is still not evidence about the
  research question.** `src/sources/base.py:273-276` sets `outcome="refused"` and
  `status=str(resp.status_code)` on any non-200, so the string is a real HTTP code that UNCTAD's
  origin returned. That is worth stating precisely because it is the exact place the
  tool-status-as-source-state rule bites: knowing the origin answered 500 licenses **no** inference
  about what UNCTAD holds.
- **Every relay null is about rendered text.** `fetch_relay.py` strips attributes, so a symbol
  present only inside a hyperlink target is invisible to this channel. The find is also
  entity-blind: a symbol rendered with an HTML entity or a non-ASCII solidus reads as absent. A
  null is "not in the rendered text of this page as this channel reduces it", never "not published".
- **Repeated fetches of one unchanged page are one observation, not many.** This applies with
  unusual force today and the analyst should look at the hashes before writing anything about
  interval or duration.
- **An UNCTAD sha256 is not a fingerprint.** Twelve re-fetches once produced twelve distinct
  digests against a clean negative control. Differing UNCTAD hashes are not evidence a page changed,
  and the mechanism is expressly unmeasured. This cuts both ways and the analyst should not import
  it to a host where it was never measured.
- **No search-synthesis figures.** No number enters this record from a search snippet.
