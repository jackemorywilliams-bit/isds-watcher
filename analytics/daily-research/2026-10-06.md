**The fact.** In GitHub Actions, cancellation is a distinct completion status, and `failure()` does not
match it; `cancelled()` is the function that does, and `always()` the one that catches both. **All four
failure alarms in this repository are gated on `failure()` alone, so not one of them can report a
cancelled job.** That is read off the committed files and does not depend on what happened Monday.

**The inference, kept separate because it is weaker.** Run #38's job concluded `cancelled`, so on the
plain reading the alert step did not execute and no mail was sent. I cannot *verify* that: the logs are
404, so I cannot see whether the step ran, and the run-level conclusion of `failure` is in tension with
the job-level `cancelled` in a way I cannot resolve from outside. **This is exactly the standing rule
about not converting a tool status into a fact about the world, applied against my own headline.**

**One cheap check settles it and it is not mine to run: Emory, did an "ISDS Thematic Watch — RUN FAILED"
email arrive on the evening of 2026-10-05?** If it did not, the alarm gap is confirmed end-to-end and the
one-line fix is urgent. If it did, the alarm works, my inference was wrong, and the question becomes why
a delivered alert produced no response — a different problem with a different remedy. **Either answer is
worth more than my guess**, which is why I am asking rather than asserting. The defect in the condition
stands on the YAML regardless of the answer.

### 3.9 AND THE SECOND ALARM CANNOT FIRE EITHER. The watchdog on the daily council is structurally incapable of reporting staleness.

**Found during the close-out, while I was checking whether anything in the instrument already watches
digest freshness before I proposed that as the day's optimization item.** The answer to that question is
no — but the search turned up something worse, and it is the same disease as §3.2 in a different organ.

`.github/workflows/heartbeat.yml` runs daily at 22:00 UTC and carries a step named **"Check
daily-meeting freshness and alert if stale"**. It is the operator's watchdog on this very routine: if the
daily council stops running or cannot push, that step is what is supposed to tell him. Its predicate:

```
# PREDICATE: .github/workflows/heartbeat.yml, the step's own Python, quoted.
stale_hours = float(os.environ.get("STALE_HOURS", "36"))
paths  = sorted(glob.glob(os.path.join("analytics", "daily-research", "*.md")))
newest = max(paths, key=os.path.getmtime)
age_h  = (now - os.path.getmtime(newest)) / 3600.0
stale  = age_h > stale_hours
```

**It keys on filesystem mtime. Git does not store mtimes.** `actions/checkout` writes every file at
checkout time, so in a fresh runner the newest record's mtime is always "a few seconds ago" **no matter
how old its content is**. Measured in this session's own fresh clone, which is the same mechanism:

```
# PREDICATE: os.path.getmtime over all 108 analytics/daily-research/*.md in a fresh clone.
analytics/daily-research/2026-06-23.md  -> mtime 2026-10-06 11:11:49   (content 105 days old)
analytics/daily-research/2026-08-08.md  -> mtime 2026-10-06 11:11:49
analytics/daily-research/2026-10-05.md  -> mtime 2026-10-06 11:11:49
distinct mtimes across all 108 records  -> 2   (clone time, plus the one file I wrote today)
the step's own computation, run here    -> age_h = 0.029 ; stale = False
```

**So `age_h` is approximately zero on every run, `stale` is False on every run, and the alert is
unreachable code.** This is not "it would have missed Monday" — it is that **no amount of staleness can
ever trigger it.** If this routine stopped running entirely, the heartbeat would report
`heartbeat OK — daily meeting is fresh.` every night indefinitely.

**The fix is one line and it is a different one line from §3.2's:** the staleness predicate must read
the newest record's **filename date** (`max(paths)` lexically, which is the correct ordering for
`YYYY-MM-DD.md` and which the same script already computes correctly elsewhere) or the newest **commit
date**, never the mtime. **I built it not. `.github/` is outside this session's merge scope and every
approval is pending.**

**Taken with §3.2, the finding generalises and this is what I want Emory to read.** This project has
three automatic alarm paths and **two of them cannot fire**: the weekly run's failure alert is gated on a
condition that does not match the status the run actually reported, and the daily council's staleness
watchdog is gated on a quantity that is constant by construction. The third — heartbeat's branch
protection check — reads live API state and works. **The pattern is that the alarms built on repository
file state are dead and the one built on an external query is alive.** That is a design lesson, not just
two bugs, and it is why I am recording it as a finding rather than filing two tickets.

**One thing this does NOT mean, and a successor must not read it in:** the alarms being dead says nothing
about whether the underlying pipelines ran. The daily council has in fact run every day — 97 delivery
markers, newest 2026-10-05 — and the weekly ran green for four weeks. **A dead alarm is a dead alarm.
It is not evidence of a dead pipeline, and it is not evidence of a healthy one either.**
