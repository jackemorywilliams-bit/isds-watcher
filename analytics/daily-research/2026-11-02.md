### 2.6 A successor hazard in the shape of the data, which I screened rather than assumed

Two properties of this record will mis-sort under filters a successor would reasonably
write, and both are instrument-level facts rather than findings about any resource.

- **`status` carries the string `"timeout"`** where all 776 other records carry an integer
  or `null`. A filter testing `status == 200` excludes it correctly. A filter testing
  `status != 200` includes it correctly. A filter that **compares or sorts** `status`
  numerically, or that reads `status` as an HTTP code, will raise or silently mislead — the
  value is the *detail* of a `no_contact`, not a code any server returned.
- **`find_matched` is absent, not false.** `r.get("find_matched")` returns `None`, so
  `not r.get("find_matched")` lumps this no-contact in with genuine find-misses, which is
  the exact conflation the relay's code comment exists to prevent. The safe test is on
  **`outcome`**: `outcome == "ok"` admits only origin answers, and `find_matched is True`
  admits only positive evidence. **`outcome` is the field that carries the layer, and it is
  the field a successor should filter on.**

My own join script survived this only because its admission predicate counts fired records
and tests `find_matched is True` for the TRUE column — i.e. by accident of a choice made
for another reason. **I record that as luck, not as design.**
